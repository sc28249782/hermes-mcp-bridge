## Quiescence — inventory เต็มก่อน switch (metadata-only, read-only)

Inventory ครอบคลุมทุก backend ที่เปิดใช้ จาก metadata registry แบบอ่านอย่างเดียว ไม่อ่าน prompt/output; `bridge_status`/recent-list ไม่ใช้เป็นหลักฐานว่าไม่มีงานค้าง; ไม่มีการ cancel, ไม่อนุมาน terminal จากอายุ, ไม่มีการแก้ status/replay/resubmit.

หลักฐานว่าไม่มีงานยังทำงาน: ตรวจ PID ที่ registry บันทึกไว้ทุกรายการ (worker/child รวม 12 identity) ยืนยันว่าไม่มี process ใดยังมีชีวิต ณ เวลาตรวจ; ตรวจ process table ไม่พบ worker ใด ๆ ของ bridge; ทุกงานที่ไม่ใช่ terminal ชัดเจนถูกตรวจรายรายการ.

### `unknown_exit` — นิยาม หลักฐาน และข้อจำกัด (คงสถานะ unknown ไว้)

- **นิยามตาม implementation**: `unknown_exit` เป็นสถานะปลายทาง (terminal lifecycle) หนึ่งในชุด terminal ของ Codex job registry — ระบบตั้งค่านี้เมื่อ worker จบลงโดยไม่มีการบันทึก exit code (เหตุ "worker จบโดยไม่มี terminal record") ผ่าน transition แบบ durable พร้อมเวลา finished
- **`unknown_exit` ไม่ใช่ความสำเร็จ** และไม่ใช่ exit code ที่ทราบค่า — ผลข้างเคียงของงานไม่ได้รับการพิสูจน์ และ registry ยังเก็บสถานะเดิมไว้ (ไม่มีการ rewrite)
- **หลักฐาน quiescence ที่ใช้**: (1) durable terminal record ใน registry (สถานะ `unknown_exit` พร้อม finished transition metadata); (2) worker/child PID ที่ registry บันทึกไว้ "ไม่มีอยู่" ใน process table ณ เวลา deployment — ตรวจ identity ตามค่าที่บันทึก ไม่ใช่ substring; (3) implementation จัด `unknown_exit` เป็น terminal lifecycle ที่ทราบแน่ชัด จึงไม่มี worker หรือ process ค้างที่อาจเขียน state
- **ข้อจำกัดที่คงไว้**: exit code/ผลลัพธ์ของงานนั้นยังเป็น unknown; ไม่ได้ใช้ "context ถูกปิด" อย่างเดียวเป็นหลักฐาน terminal; ไม่ได้ใช้อายุงานหรือ upstream 404 เป็นหลักฐาน; ไม่มีการเปลี่ยนสถานะใน DB ทั้งสิ้น. ใน private receipt ระบุชัดว่าข้อค้นพบนี้ถูกนับเป็น terminal-with-unknown-outcome ตามหลักฐาน 3 ข้อข้างต้น — ไม่ใช่ blanket pass และไม่อ้างว่างานสำเร็จ

## Stop, backup และ switch

- หยุด production chain แบบ exact identity: ตรวจ executable, absolute argv, parent/child ownership และ start identity ซ้ำก่อนสั่ง stop ทุกครั้ง ไม่ใช้ substring match/killall; ทุก process จบด้วย graceful TERM ไม่ต้องใช้ KILL; ไม่หยุด process ของ Dev หรืองานอื่น
- Control plane: Dev control ที่ผ่านการ verify อิสระ (health + version pin `e7add7e…` + probe) เป็นผู้ทำ stop/switch ตามทางเลือก (ii) ของแผน; ไม่มีการตัด parent control กลางงาน — งาน control ของ parent จบก่อน final inventory ทุกชุด
- Backup หลัง quiescent: คัดลอก config/state ครบ (รวม log และ SQLite ทุกไฟล์ ไม่มี sidecar ค้าง ณ เวลา copy) เป็น private backup mode 0700/0600 และสำเนาสำหรับ instance ใหม่; **ตรวจ hash ตรงกัน 16/16 ไฟล์** ระหว่างต้นทาง/backup/สำเนา instance ใหม่ ก่อน start; ไม่มี DB merge/replay/resubmit; ไม่คัดลอกฐานข้อมูลที่ยังมี writer
- Switch: profile launch command เปลี่ยนไปยัง deployment directory ใหม่ (ชื่อไม่ชนกับ signing clone ของ operator ซึ่งไม่ถูกแตะ) แบบ atomic คง mode 0600 พร้อม backup ก่อนแก้; config/permission/schema ไม่เปลี่ยนทุกค่า (OpenCode opt-in ครบ, Hands คง disabled); รีสตาร์ตผ่าน auth flow เดิม (tunnel id เดิม, runtime key path เดิม); ไม่ติดตั้ง init unit ใหม่

- Parent connector inventory เปิด 33 production tools ตาม config (รวม OpenCode tools) — **เป็น inventory ของ connector เท่านั้น ไม่ใช่ raw wire `tools/list` capture** และไม่ใช่ independent wire discovery acceptance; canonical default discovery ยังเป็น 27

- `unknown_exit`: ผลลัพธ์ของงานยังเป็น unknown ตามที่ระบุข้างต้น; สถานะใน registry คงเดิม

- ไม่ส่ง native model job หรือ live oversized output เพื่อทดสอบ production; Hands v1.3.0 capability gate และ MCP Events BLOCKED คงเดิม

## Rollback และงานค้าง

Deployment เสร็จสิ้น; production รัน signed v1.2.8. เก็บรักษา: deployment v1.2.7 เดิม, private backup แบบ quiescent และ backup ของ profile config ก่อน switch; signing clone ของ operator ไม่ถูกแตะ.
หากต้อง rollback ให้หยุดรับงานและตรวจ active jobs/process ก่อน หยุด instance ใหม่เมื่อปลอดภัย คืน profile command เป็น v1.2.7 แล้ว restart ผ่าน auth flow เดิม. ห้ามรวม state ต่างชุดหรือ replay งาน; หากมีการเขียน state ใหม่หลัง switch ต้องตรวจผลกระทบก่อนเลือก snapshot.
งานค้างเดิมเปิดตาม [release record](V1.2.8-RELEASE-RECORD-TH.md): P2 apply/delete, Hands v1.3.0, MCP Events (BLOCKED) และ open gaps ของ §21 (submit admission, crash-between-submit-and-bind, non-closed binding ack/recovery, uncertain replay).
