## Compatibility และ operational disclosure

- หลังอัปเกรด default soft-cap เป็น 1,000 แม้ไม่มี `contexts` ใน config. มี observation บน status/create โดยไม่ต้องเปิด execution capability ใหม่. หากมี `contexts` ต้องเป็น object. ค่า optional `contexts.soft_cap` ต้องเป็น integer 1–100,000; boolean และค่าผิด range ถูก reject.
- Status/create เพิ่ม aggregate `registry` 6 fields. `bridge_status.ok=false` เมื่อ registry observation unavailable. ถึง soft-cap อย่างเดียวเป็น warning และ root ok ยังเป็น true. Monitoring ต้องแยกสองกรณีนี้.
- เมื่อ create บันทึกสำเร็จแล้วแต่ observation fail ให้ใช้ acknowledgement/context เดิม. อย่า retry create เพียงเพราะ registry unavailable. Status/recent ของ context คง metadata semantics เดิม.
- Observer ไม่ดึง labels/refs/IDs มารายงาน แต่ไม่ได้ redact metadata เดิมของ create/status/recent ทั้ง response. ข้อจำกัด plaintext storage และ untrusted content เดิมไม่เปลี่ยน.
- CLI preview เป็น local-only, รับ existing absolute state directory, ใช้ closed cutoff กับ four-NULL predicate และไม่มี apply. ไม่ compact backend/chat history. ไม่มีหลักฐานว่า P1 แก้ปัญหา Connection interrupted ของ Work chat.
- SQLite mode=ro ไม่ใช่ filesystem-wide no-write guarantee. SQLite อาจใช้ locks/shared memory/sidecars. Lock timeout ไม่ใช่ whole-call deadline; logical sample/batch ไม่ใช่ total scan/I/O bound. หากอ่านไม่ได้ให้ constant unavailable; ห้ามใช้ immutable/nolock/write fallback.
- Dedicated read-only mount probe ยังไม่ได้ทำ. Evidence ที่ review แล้วครอบคลุม read-only SQL, POSIX file/directory permissions, WAL และ lock cases ตาม record. การตัดสิน scope ไม่เปลี่ยน MUST ของ §20 หรือเปลี่ยนผลที่ยังไม่ทดสอบเป็น PASS.
- Codex result ใช้ raw reads แทน buffered prefetch. Truncation/read failure อาจจบด้วย constant error แทนการคืน prefetched bytes. ไม่รับรอง immutable snapshot, detection ของทุก overwrite หรือการเปลี่ยนหลังอ่านจบ. Limits/ownership/decoding เดิมคงอยู่.
- P1 ไม่มี cleanup, deletion, quota enforcement หรือ hard-cap rejection. จำนวน rows สูงไม่ได้แปลว่า backend task จบแล้ว และไม่ใช้ HTTP 404 เป็น terminal evidence.

## ขั้นตอนหลัง scope ได้รับอนุมัติ

1. ใช้ approved scope ตาม decision นี้ในการเตรียม release. หากต้องเปลี่ยน scope ให้บันทึก operator decision ใหม่ตาม change control; อย่าขยายการอนุมัติ scope เป็น signing/deployment approval.
2. เปิด release-preparation PR แยกตาม scope ที่อนุมัติแล้ว. เลือก reviewed build input หลัง decision และทบทวนเอกสารตาม documentation gate. จัด stamp/descriptive status, source tests, exact-head CI 3.12/3.14 และ candidate archive/extracted-tree verification ตาม [release runbook](RELEASE-RUNBOOK-TH.md).
3. Candidate archive ยังไม่ใช่ signed release. แยก embedded build-input identity ออกจาก final signed-tag target. บันทึก candidate checksum ใน PR receipt เพื่อเลี่ยง self-reference ใน source tree.
4. หลัง prep review/merge ขอ operator อนุมัติ final target และ signing/publication. ตรวจ target, clean tree และ absent-tag outcome ใหม่; network error ไม่ใช่ tag absence.
5. ทำ GPG TTY/Git-identity preflight และ signed tag ผ่าน operator interactive terminal เท่านั้น. ห้าม key/passphrase เข้า chat/bridge. ตรวจ signature และ peeled commit; ห้ามแทน tag ที่เผยแพร่แล้ว.
6. สร้าง assets จาก signed tag, ตรวจ ZIP/manifest, offline stamp, fresh download และ byte-identical rebuild. บันทึก signature verification แยกจาก GitHub badge ตามผลจริง. ขอ independent fresh-input audit ตาม release workflow.
7. เปิด Phase C record โดยไม่เปลี่ยน signed tag/assets. หลักฐาน preparation/source/extracted/live แต่ละชุดต้องผูกกับ head และ scope เดิม.
8. บันทึก deployment decision แยก รวมตัวเลือกยังไม่ deploy. หากอนุมัติ upgrade ให้ตรวจ active/unknown jobs, private backup, original launch และ rollback directory ก่อน maintenance. เก็บไดเรกทอรีเดิมไว้ใช้ rollback.
9. หลัง upgrade ตรวจ signed-archive identity/stamp, config/schema, private modes, watchdog/health/discovery และ applicable P1 acceptance ด้วย isolated synthetic state. ตรวจ native/backend/model acceptance เฉพาะเมื่อได้รับอนุมัติ scope นั้น; identity check ไม่ใช่ model-task acceptance.
10. หาก target หรือ acceptance ไม่ผ่าน ให้ห้ามเริ่มงานใหม่และคืน deployment เดิมตาม [upgrade guide](UPGRADE-TH.md). บันทึกผลที่ตรวจสอบได้จริงและข้อจำกัดก่อนปิด release/deployment record.

Privacy follow-up ของ v1.2.6 ปิดตาม §19.4 แล้ว; proposal นี้ไม่ reopen หรือขยาย closure เดิม.
