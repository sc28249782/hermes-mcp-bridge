# V1.2.4 MCP Events capability probe — Dev acceptance

## Status and scope

This document defines the **capability gate** for v1.2.4. The repository also contains a disposable Dev fixture for this probe. The fixture is not a bridge runtime event capability: it has no Hermes terminal observer, no persistent subscription state, no new MCP tool, and no production activation.

When and only when the Dev operator starts it with `BRIDGE_EVENTS_PROBE=1`, the fixture sends its verification and one redacted test event to the allowlisted callback. The normal bridge never sends an outbound callback.

Run this probe only with **Hermes Local Bridge - Dev** and its Dev Secure MCP Tunnel. Do not modify the production profile, production tunnel, production bridge directory, or production ChatGPT plugin.

The normal bridge remains at the existing 27-tool discovery contract during this phase. While the fixture is active, it intentionally replaces the Dev tool server and advertises no ordinary tools.

## Dev fixture activation

The fixture is Dev-only and opt-in:

```bash
BRIDGE_EVENTS_PROBE=1 \
BRIDGE_EVENTS_PROBE_ALLOWED_HOSTS='' \
tunnel-client run --profile hermes-wsl-dev \
  --health.listen-addr 127.0.0.1:8081
```

The allowlist environment value is comma-separated and accepts only an exact DNS host or a `*.suffix` entry. It is empty by default, so a probe subscription is denied before any callback is sent. Keep it empty while diagnosing whether `events/subscribe` reaches the fixture. Do not place a callback URL or a signing secret in the shell history, repository, audit, or acceptance record. Before any outbound callback test, address connection-time DNS validation and TLS hostname preservation; the current fixture resolves at subscribe time and its HTTP client may resolve again at connect time.

The fixture is in-memory and emits `bridge.probe.ready` only after challenge verification. It proves tunnel/protocol/callback interoperability only. It does **not** satisfy the persistent ownership, expiry, refresh, retry, or Hermes-terminal delivery requirements of a runtime release.

## Decision rule

Proceed to subscription and delivery implementation only when all three checks below pass with recorded evidence.

1. ChatGPT Work and the Dev Secure MCP Tunnel exchange MCP Events protocol 2.0 requests on the authenticated endpoint.
2. WSL2 can verify and deliver a signed HTTPS callback to the ChatGPT-supplied destination without opening an inbound public service.
3. A Work chat can discover an event, subscribe, receive one signed redacted test event, and unsubscribe.

If any check fails, record the exact protocol or transport failure and stop the v1.2.4 runtime track. The allowed fallback is user-directed, explicit `hermes_task_status` polling. The bridge MUST NOT call that polling push notification.

## Proposed configuration contract

The following is a target contract for a later runtime PR. The current bridge MUST NOT act on it yet.

```json
{
  "events": {
    "enabled": false,
    "callback_host_allowlist": []
  }
}
```

- `events.enabled` defaults to `false`.
- A disabled feature MUST make no outbound callback.
- An enabled feature with an empty allowlist MUST deny every callback and must expose only a redacted configuration error.
- Allowlist values must come from local operator configuration. A model, prompt, subscription argument, or event payload MUST NOT add or change an allowlist value.

## Callback host matching

The fixture and later validator MUST canonicalize a DNS host before matching. They MUST reject IP literals, empty values, user-info, non-HTTPS URLs, and every explicit port other than `443`.

Allowlist entries use one of these forms:

| Entry | Meaning |
| --- | --- |
| `chatgpt.example.com` | exact host only |
| `*.openai.com` | one or more subdomain labels under `openai.com`; it does not match `openai.com` itself |

Matching is label-boundary based. For example, `*.openai.com` may match `events.openai.com` but MUST NOT match `evil-openai.com`. A suffix is not a substring match.

The allowlist is the authorization decision. HTTPS, public-address validation at connection time, redirect refusal, timeout, and TLS hostname verification are additional defenses and MUST NOT turn an otherwise unauthorized host into an authorized one.

## Principal and data boundaries

A future subscription is allowed only from an authenticated MCP Events request delivered through the Dev tunnel after the user confirms monitoring in the Work chat.

No ordinary MCP tool or local CLI command may create a subscription, accept an arbitrary callback URL, reveal a callback URL, or reveal a signing secret. The model cannot create subscriptions indirectly through a prompt.

The probe and future implementation must not put a callback URL, signing secret, prompt, output, credential, detailed filesystem path, or terminal-result content in audit, diagnostics, tool results, or event payloads.
